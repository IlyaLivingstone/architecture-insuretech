# Задание 4. Проектирование продажи ОСАГО

Сценарий: клиент заполняет заявку на ОСАГО, `osago-aggregator` рассылает её страховым компаниям
и по мере получения ответов передаёт предложения в `core-app`, который показывает их пользователю
сразу, не дожидаясь остальных. Максимальное время ожидания решения от страховой — 60 секунд,
пик — 2,5 тысячи одновременных пользователей.

## Решения по пунктам задания

1. **Реализация `osago-aggregator`** — отдельный сервис (Kotlin/SpringBoot). К страховым компаниям
   ходит по их однотипному REST API с двумя эндпоинтами: `POST create-application` (создать заявку)
   и `GET offer` (получить предложение). По каждой заявке агрегатор создаёт заявку у каждой компании
   и опрашивает её до получения решения или истечения 60 секунд.

2. **Хранилище — да**, собственная БД `osago-db` (PostgreSQL). В ней хранится техническое состояние
   заявки: `applicationId`, статус по каждой страховой компании, срок следующего опроса
   (`retryDeadline`), последний полученный результат. Причина: сервис запущен в нескольких репликах,
   а состояние заявки должно переживать рестарты и «переезжать» между репликами.

3. **API для `core-app`.** Команда — синхронный `POST /osago/applications` (создать заявку, вернуть
   `applicationId`, вернуться сразу). Результаты — не синхронно, а потоком событий через Kafka
   (см. п. 4), потому что предложения приходят порциями в течение 60 секунд.

4. **Интеграция `core-app ↔ osago-aggregator`.** Команда — короткий синхронный REST (мгновенный
   ответ-подтверждение). Результаты — асинхронно через Kafka, топик `osago.proposals` (событие
   `OsagoProposalReady` по каждому полученному предложению, ключ — `applicationId`).
   Такой выбор убирает «async внутри sync»: синхронный запрос не блокируется в ожидании
   асинхронных ответов страховых.

5. **API для веб-приложения в `core-app`.** `POST /api/osago/application` (REST — создать заявку)
   и `GET /api/osago/application/{id}/stream` (SSE — поток предложений).

6. **Интеграция веб-приложение ↔ `core-app`.** REST для создания заявки + **SSE** для получения
   предложений по мере их поступления. SSE выбран как простой односторонний server push
   (авто-переподключение, не требует двустороннего канала); лимит «6 SSE-соединений на браузер»
   здесь не мешает — на заявку одно соединение.

7. **Паттерны отказоустойчивости** (обозначения на схеме):
   - **Timeout** — 60 с общий бюджет на заявку и отдельные таймауты на каждый вызов к страховой;
   - **Retry** — повтор `create-application`/`offer` с экспоненциальной задержкой, идемпотентно
     (уникальный ключ операции);
   - **Circuit Breaker** — на каждую страховую компанию: после серии ошибок вызовы к ней
     временно отключаются, чтобы не блокировать остальных;
   - **Rate Limiting** — на публичном API `core-app` (ограничение числа одновременных заявок),
     плюс лимиты исходящих вызовов к страховым компаниям.

8. **Несколько экземпляров сервисов.** SSE-соединение живёт на конкретной реплике `core-app`,
   а событие `osago.proposals` из Kafka может прийти на любую реплику. Решение: события партиционируются
   по `applicationId`, а реплика, держащая SSE-соединение, подписывается на предложения своей заявки
   (общий канал pub/sub, например Redis, или sticky-балансировка на gateway). `osago-aggregator`
   хранит состояние заявки в `osago-db`, поэтому любой его экземпляр может продолжить опрос
   страховых после рестарта другого.
